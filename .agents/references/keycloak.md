# Reference: Keycloak

- **Project:** [keycloak/keycloak](https://github.com/keycloak/keycloak) — Red Hat's open-source IAM (Java).
- **Docs:** https://www.keycloak.org/documentation
- **Why referenced:** occasional design cross-checks (parity/posture comparisons); authup's primary
  parity target is Authentik (see `authentik.md`), Keycloak is consulted for OIDC/credential-storage
  precedent.
- **How to maintain:** when you look something up in Keycloak's docs/source during authup work, add
  or correct the mapping row here (cumulative). Pin claims to a version/date.

## Concept map (Keycloak → authup)

| Keycloak concept | authup counterpart | Behavioral differences / notes |
|---|---|---|
| User OTP secret storage: `CREDENTIAL` table, `SECRET_DATA` JSON column — **plaintext** (`{"value":"<seed>"}`; confirmed in [discussion #23207](https://github.com/keycloak/keycloak/discussions/23207), verified 2026-07-14) | `auth_user_authenticators.secret` — AES-256-GCM under the per-realm enc key from the realm key store (`auth_keys` `use=enc`, auto-generated, optionally KEK-wrapped via env `SECRETS_ENCRYPTION_KEY`; `select:false`) | authup encrypts TOTP seeds at rest; Keycloak does not (delegates to DB/disk encryption). |
| Realm keys (signing/encryption): generated per realm, private keys stored in `COMPONENT_CONFIG` — plaintext | `auth_keys.decryption_key` — plaintext base64, `select:false` only | Parity (both plaintext). Keycloak's own [secure-credentials-store design doc](https://github.com/keycloak/keycloak-community/blob/main/design/secure-credentials-store.md) lists realm keys, client secrets, LDAP/SMTP creds, IdP secrets, and user OTP secrets as "currently stored in plaintext". |
| Vault SPI (`${vault.key}` references) — **config-level secrets only** (SMTP password, LDAP bind credential, IdP client secrets); read-only lookup, shipped as Part I of the secure-credentials-store design | No vault indirection for config secrets; env/config values used directly | Part II of that design (an encryption/decryption SPI for DB-stored secrets, i.e. envelope encryption) was drafted but **never implemented** — Keycloak still stores user OTP secrets plaintext as of 2026. |
| Session device attribution: `UserSessionModel` exposes `getIpAddress()` with **no setter** (`server-spi/src/main/java/org/keycloak/models/UserSessionModel.java`, `main`, verified 2026-08-07). The address is fixed when the session is created / restarted (`restartSession(..., ipAddress, ...)`); a token refresh only moves `setLastSessionRefresh(int)` | `auth_sessions.ip_address` / `user_agent` pinned at creation; the refresh grant slides `refreshedAt` / `seenAt` / `expiresAt` only, and records the refreshing request on the `auth_session_tokens` row instead | **Aligned.** authup used to overwrite both columns from the refreshing request, which let a server-side refresher (the Nuxt console resolving the store during SSR) repaint a user's session as `node` plus the renderer's address. Keycloak's read-only accessor is the same call: the device belongs to the session, and refresh freshness is a separate field. |
| Event persistence: user (login) + admin events **not saved by default** (fire-only; written to server log via the built-in `jboss-logging` listener). When "Save events" is enabled per realm, `Expiration` defaults to **0 = never expire** (no default retention — [GH #47016](https://github.com/keycloak/keycloak/issues/47016), open as of 2026-07-16); current versions expose a separate admin-events Expiration (older ones lacked it, [GH #12476](https://github.com/keycloak/keycloak/issues/12476) stalled). Community guidance: short window (7–30 d) + external SIEM for long-term. | `auth_events`: persisted by default (`eventLogEnabled: true`), security events 90 d (`eventLogRetentionDays`, raiseable via config/env), entity-CRUD mirror 7 d (`eventLogEntityRetentionDays`), per-row `expires_at` + minute sweep; structured log line always fires (SIEM path) | authup is opt-out with bounded retention; Keycloak is opt-in with unbounded retention (table grows forever unless Expiration is set — known operational footgun). authup's default was 365 d (Authentik parity) until 2026-07-16, lowered to 90 d (Okta-parity, hosted-provider posture). Verified 2026-07-16. |
| Per-IdP "Post login flow": a brokered login runs no OTP form by default; an operator adds one (with its own LoA/step-up conditions) per identity provider | A federated login returns to the hosted `/authorize` page for consent and the prompt gates, but takes no local factor and no inline enrollment (plan 094, issue #3454) | Same default as Keycloak. authup's one addition is that an explicit `acr_values=urn:authup:mfa` still triggers the local factor, since the application asked for a proof authup can produce. Since issue #3477 authup additionally verifies the upstream's own `amr`/`acr` per provider (opt-in `requiredAmr` / `requiredAcr`, unset by default), which makes "the upstream guarantees it" checkable rather than assumed. **Scoped claim:** Keycloak's OIDC identity-provider configuration exposes no option that validates the upstream id_token's `amr`/`acr` against an operator-configured allow-list *before* the brokered identity is provisioned — [`identity-broker/oidc.adoc`](https://github.com/keycloak/keycloak/blob/main/docs/documentation/server_admin/topics/identity-broker/oidc.adoc) at `main` mentions neither claim (verified 2026-08-19). Its adjacent mechanisms are mapping and propagation rather than a gate: `oidc-acr-mapper` / `oidc-amr-mapper` put claims into Keycloak-issued tokens, IdP mappers copy upstream claims into session notes, and [ACR-to-LoA mapping](https://github.com/keycloak/keycloak/blob/main/docs/documentation/server_admin/topics/login-settings/acr-to-loa-mapping.adoc) is realm-level. Enforcement there needs a custom `first broker login` execution. The outbound half has a counterpart: Keycloak's per-IdP *Forwarded query parameters* can carry `acr_values` upstream, which is what authup derives from `requiredAcr`. |
| Brokered-login continuation: the auth session is looked up by the `AUTH_SESSION_ID` cookie and the URL's `session_code` is a secret INSIDE it, single-use and constant-time compared (`CodeGenerateUtil.parseSession` / `#L104-L152`); the login UI is server-rendered FreeMarker, there is no login SPA | The pending login rides the `authup_federated_login` cookie and the hosted SPA completes it with a same-origin POST | Same posture, verified at `main` 2026-08-19: neither product hands a front end a one-time value to trade for a session. Keycloak additionally signs the cookie value since 26.1, and a valid `state` alone never completes a login (`SessionCodeChecks` falls back to a fresh auth session and a "Login timeout" page). |
| Identity-provider config storage: `IDENTITY_PROVIDER` holds only scalars (`PROVIDER_ALIAS`, `PROVIDER_ID`, `PROVIDER_DISPLAY_NAME`, `ENABLED`, `TRUST_EMAIL`, `LINK_ONLY`, `HIDE_ON_LOGIN`, `ORGANIZATION_ID`, the two broker-flow ids, ...). Everything protocol-specific (`clientId`, `clientSecret`, `tokenUrl`, `authorizationUrl`, `userInfoUrl`, `defaultScope`) lives in a key-value side table, `IDENTITY_PROVIDER_CONFIG(IDENTITY_PROVIDER_ID, NAME, VALUE TEXT)`, mapped by an `@ElementCollection` on `IdentityProviderEntity.config` (verified at tag `26.7.2`) | `auth_identity_providers` (~9 scalar columns) plus the EA side table `auth_identity_provider_attributes`, spliced onto the entity by `extendOneWithEA` inside `findOneById` / `findOneByName` | **Identical storage shape.** Keycloak's config map is the direct analogue of authup's EA rows: a generic string/string bag hanging off the provider row, invisible to any column-level or query-level allow-list. Which is why Keycloak protects it one layer up, at the representation, rather than at the query (next row). |
| Admin-API masking of the IdP secret: `StripSecretsUtils.stripBroker(rep)` runs `stripFromMap(rep.getConfig(), "clientSecret")`, replacing the value with `ComponentRepresentation.SECRET_VALUE = "**********"`. `maskNonVaultValue` leaves a `${vault.…}` reference verbatim (a pointer is not a secret) and masks everything else; `stripFromMap` only rewrites a key that is already present, so the shape of the map is unchanged. It is wired through a `REPRESENTATION_FORMATTER` map keyed by representation class, so it applies to the single read (`GET /admin/realms/{realm}/identity-provider/instances/{alias}`), to the list (`briefRepresentation=false`; `true` bypasses the strip but `toBriefRepresentation` carries no config at all), and to realm export. The write path restores it: `IdentityProviderResource.updateIdpFromRep` puts the previously stored value back whenever the submitted `clientSecret` equals the placeholder. Both endpoints additionally require `auth.realm().requireViewIdentityProviders()` / `requireManageIdentityProviders()`, so there is no anonymous JSON IdP surface at all (all verified at tag `26.7.2`) | `GET /identity-providers/:id` is anonymous (`@DGet('/:id', [])`, its `IDENTITY_PROVIDER_READ` evaluate swallowed in `catch {}`) and returns the EA rows unmasked, issue #3480 | **Opposite posture, and the fix template.** Keycloak defends the same data twice: the endpoint is admin-only, and even a permitted admin gets `**********`. The mask is a hardcoded key DENYLIST applied where the representation is built, deliberately not at the query layer, because the query layer cannot see into a key-value bag (exactly authup's constraint: a rapiq `fields.validateMany` gate works for the `client.secret` COLUMN and is inexpressible for an EA value). The `**********` sentinel plus restore-on-update is the cohort's canonical answer to "mask on read, still writable". |
| What the browser login page learns about configured IdPs: nothing over JSON. The list is rendered server-side into the FreeMarker login template at the authorization endpoint (`/realms/{realm}/protocol/openid-connect/auth`); `login.ftl`'s `socialProviders` section reads exactly `p.alias`, `p.displayName`, `p.iconClasses` and `p.loginUrl`. `IdentityProviderBean.IdentityProvider` carries `alias`, `displayName`, `providerId`, `loginUrl`, `guiOrder`, `iconClasses`, `themeConfig`, and `createIdentityProvider` is the filter: of the whole config map only entries prefixed `kcTheme-` are copied into `themeConfig`. `loginUrl` is Keycloak's OWN broker endpoint (`Urls.identityProviderAuthnRequest` -> `/realms/{realm}/broker/{alias}/login`), so not even the upstream `clientId` reaches the page; it first appears in the subsequent 302 to the upstream, where it is public by OAuth2 design. `HIDE_ON_LOGIN` filters rows out of the bean (verified at `main`, 2026-08-19; current release 26.7.2) | The SSR `/authorize` page renders the provider list through the kit's `ALoginForm`, and `GET /identity-providers` (the collection, whose `findMany` does NOT call `extendOneWithEA`) is anonymous | Aligned on what the browser is entitled to: a label, an icon, and a link. Keycloak hands over four template values and never a serialized provider entity, which is the same cut authup's collection route already makes by not extending EA. #3480 is therefore a record-route defect, not a design gap: the two routes differ by exactly the `extendOneWithEA` call. |
| Token introspection auth (whole row from memory, 2026-08-23, not re-verified against source; `TokenIntrospectionEndpoint`, ≈ 20.x-26.x): the caller authenticates through the client-authenticator chain (secret Basic/body, client-jwt, x509); a bearer is NOT accepted as caller authorization, and an authenticated PUBLIC client is refused outright ("Public client is not allowed to introspect", 401). Revocation (`TokenRevocationEndpoint`): same chain, but public clients ARE accepted by `client_id` alone, with the token's `azp` checked against the caller ("Unmatching clients"). Keycloak's own admin console (public `security-admin-console`) never introspects: keycloak-js parses the JWT locally and refreshes via the token endpoint | `TokenController.assertIntrospectionAuthorized` + `isIntrospectionAllowed` (#3489: authenticate, then self / issued-for client / realm-scoped `TOKEN_INTROSPECT` grant, deny = bare `active: false`): a request identity (live bearer or Basic) OR confidential client credentials (`secret` or `tls` certificate evidence); `authMethod: none` refused; `/token/revoke` ungated | authup additionally accepts a bearer, which RFC 7662 §2.1 names and Keycloak does not, because the secret-less consoles and the kit introspect their own live token and have no other credential. On revocation authup is LOOSER than Keycloak (no `client_id`, no ownership check): the kit revokes anonymously during logout teardown and a public client's `client_id` proves nothing anyway. |
| Admin console delivery (verified 2026-08-25 against the `keycloak/keycloak` repo README of `js/apps/admin-ui` and keycloak.org *Creating your own Console*): a React + PatternFly SPA built with Vite, published as `@keycloak/keycloak-admin-ui`, served by the Keycloak server itself at `/admin/<realm>/console/` as static assets against the admin REST API; no SSR (only the login pages are server-rendered FreeMarker). The account console is a React SPA the same way | `apps/client-admin-console`: a Vite/Vue SPA served by server-core at `<publicUrl>/console/admin` (plan 081, `/console/admin` since plan 099), runtime config spliced into `index.html` per request; the account console at `/console/account` has the same shape | Same posture. Keycloak's console authenticates with `keycloak-js` (a JS-held token pair); authup's served consoles hold no token in JavaScript and ride the opaque session cookie (plan 088). |
| Client `rootUrl` / `baseUrl` (`ClientRepresentation`, from memory, 2026-09-02, not re-verified against source): `rootUrl` is a prefix that relative `baseUrl`, redirect URI and admin URL values resolve against (`${rootUrl}` substitution), and `baseUrl` is the link the account console's Applications page renders | `Client.baseUrl` only, since #3355: the application's home URL, rendered as an http(s)-only link on the account console's Applications page. `rootUrl` was dropped (authup's redirect patterns are absolute, so a root resolved nothing) and the text `scope` column with it (`auth_client_scopes` is the only scope source) | Same user-facing purpose for `baseUrl`. authup skips the prefix mechanism because nothing relative exists to anchor. |
| Back-channel logout (OIDC Back-Channel Logout 1.0; from memory, 2026-09-02, not re-verified): per-client *Backchannel logout URL*, plus *session required* and *revoke offline sessions* toggles; the logout token carries `sid` when the session toggle is on and is pushed on user logout, session expiry included; front-channel logout offered alongside | `Client.backchannelLogoutUri` (plan 064 Stage 2): `SessionManager.revoke` is the one chokepoint, `logout_token` always carries `sid`, `events`, no `nonce`; `Promise.allSettled` with a 5s timeout, best effort | authup emits on explicit revocation only (management API, `/logout` hint, refresh-replay family revoke), never on expiry or a DB cascade; no per-client session toggle since `sid` is always present; front-channel rejected (iframe tech); the `typ: logout+jwt` header is not set yet; the delivery audit event is deferred (Stage 3). |
