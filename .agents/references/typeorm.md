# typeorm / typeorm-extension — reference mapping

Upstream: `github.com/typeorm/typeorm` (community, **not** tada5hi — no fast
turnaround, treat its quirks as fixed constraints) and
`github.com/tada5hi/typeorm-extension` (tada5hi — file issues freely).
Workspace pins: `typeorm` 1.1.0, `typeorm-extension` ^4.0.0-beta.3.

| typeorm (source) | authup (consumer) | Notes |
|---|---|---|
| `MysqlDriver.getColumnLength` (`driver/mysql/MysqlDriver.js`) | every `@Column({ type: 'uuid' })` on an entity | MySQL has no uuid type (`uuidColumnTypeSuported` is true only on **MariaDB ≥ 10.7**), so `uuid` normalizes to `varchar`. The driver returns `36` **only** when `generationStrategy === 'uuid'` (`@PrimaryGeneratedColumn('uuid')`); a plain FK/relation uuid column falls through to the generic varchar default **255**. Hence `auth_users.id` is `varchar(36)` while `auth_users.realm_id` is `varchar(255)` — both correct, both derived. Migration `1785940000000-AlignSchemaWithEntityMetadata` widened the 15 columns where hand-authored migrations wrote `varchar(36)`. Upstream fix for the non-generated case (typeorm#1139) only ever covered the generated one. |
| `EntityMetadataValidator.validate` (`metadata-builder/`) | — (blocks pinning `length` on uuid columns) | `if (column.length && !driver.withLengthColumnTypes.includes(normalizedColumn)) throw` — so `@Column({ type: 'uuid', length: 36 })` fails at `DataSource.initialize()` on postgres with `Column X of Entity Y does not support length property.` (verified empirically 2026-07-29). **This is the hard reason the MySQL uuid width cannot be fixed from the entity side** — the app would not boot on postgres at all. `uuid` is absent from postgres's `withLengthColumnTypes`; on MySQL the same column normalizes to `varchar`, which accepts a length, so it passes there. |
| `PostgresDriver.createFullType` (`driver/postgres/PostgresDriver.js:1011`) | — | Appends `(length)` whenever `column.length` is set without consulting `withLengthColumnTypes`, so a direct call renders `uuid(36)`. Unreachable from entities (the validator above throws first) and from introspection (query runners read a length back only for `withLengthColumnTypes`), i.e. an API-level inconsistency rather than a live bug — postgres + cockroachdb read `column.length` directly, mysql/oracle/sqlserver render through `getColumnLength`. Filed as **typeorm/typeorm#12741**, fix in **typeorm/typeorm#12742**. Community repo — treat as a fixed constraint regardless. |
| `RdbmsSchemaBuilder.log()` (via `dataSource.driver.createSchemaBuilder()`) | — (upstream mechanism; the gate calls typeorm-extension's `getSchemaDrift`, which wraps it) | Returns the statements that would reconcile the live schema with the entity metadata. Zero = migrated schema matches the model. Wired as the 4th step of the `tests-migrations` CI job; also the tool that found both wrong-target FKs and the naming/type split. With the chain applied, `migration generate` correspondingly writes **no file**. |
| `ColumnMetadata.generationStrategy` | `@PrimaryGeneratedColumn('uuid')` vs `@PrimaryColumn({ type: 'uuid' })` | The distinction is load-bearing for the width above: `auth_consents.id` (generated) is 36, `auth_events.id` / `auth_session_tokens.id` (app-provided ids) are 255. |

| typeorm-extension (source) | authup (consumer) | Notes |
|---|---|---|
| `synchronizeDatabaseSchema` (`src/database/methods`) | `app/modules/database/module.ts` → `DatabaseModule.migrate` | Runs `runMigrations({ transaction: migrationsTransactionMode })` when the options carry migrations, else `synchronize(false)`. So for mysql/postgres **boot applies pending migrations** — a failing migration is a failed startup, not a CLI error. sqlite has `migrations: []` and synchronizes. |
| `generateMigration` (`src/migration`) | `apps/server-core/src/cli/commands/migration.ts` → `migration generate` | Drops + recreates a local `migrations` database per dialect, replays the chain, diffs against the compiled entities, writes **both** dialect files under one shared timestamp, `prettify: true`. Hardcoded local connections matching `docker-compose.yml` (postgres 5432 / mysql 3306, `start123`). Emits nothing when there is no diff. This is the only sanctioned way to author DDL (conventions.md). |
| `assertSchemaMatchesMetadata` / `getSchemaDrift` (4.0.0-beta.2) | `scripts/assert-schema-drift.mjs` | The gate calls `assertSchemaMatchesMetadata(options, { skipWithoutMigrations: true })`, which throws `SchemaDriftError` listing the reconciling statements; `skipWithoutMigrations` skips sqlite for free. Shipped in beta.2 (tada5hi/typeorm-extension#1422) in response to **#1420**, filed from this work. The `typeorm-extension db drift` CLI does the same job but discovers a DataSource from a **file**, while authup builds its options programmatically (`DataSourceOptionsBuilder` injects entities, migrations and subscribers around the env-derived connection), so the thin script stays. |
| `renameIndex` / `renameForeignKey` / `changeColumnType` / `withForeignKeyChecksDisabled` (4.0.0-beta.2, beta.3) | **not consumed** | Guarded, idempotent rename/widen helpers, filed and shipped from this work (#1420 -> #1422, #1424 -> #1425). `1785940000000` was first written on top of them and then rewritten as plain SQL: a migration should be a list of statements, not a program, and the idempotence they buy is a property no other migration in the chain has (the `migrations` table is what prevents re-runs). Reach for them if a future repair genuinely needs to resume mid-run. |
| `MysqlQueryRunner.changeColumn` (typeorm) | — (why `1785940000000` writes `MODIFY COLUMN` by hand) | It DROPs and re-ADDs a column whose length differs, so a widening empties the column on a populated table and fails outright on a foreign key column (`ER_FK_COLUMN_CANNOT_DROP`, even with the checks disabled). This is also why a generated mysql migration for the width drift was data loss rather than a widening. |
| `assertSchemaMatchesEntity` (`@rapiq/adapter-typeorm`, not this package) | `app/modules/database/repositories/schema-validation.ts` | Different axis: validates rapiq query **schemas** against entity metadata at boot. The drift gate validates the **migrated database** against entity metadata in CI. Both are needed. |
