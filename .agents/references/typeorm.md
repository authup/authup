# typeorm / typeorm-extension — reference mapping

Upstream: `github.com/typeorm/typeorm` (community, **not** tada5hi — no fast
turnaround, treat its quirks as fixed constraints) and
`github.com/tada5hi/typeorm-extension` (tada5hi — file issues freely).
Workspace pins: `typeorm` 1.1.0, `typeorm-extension` ^4.0.0-beta.3.

| typeorm (source) | authup (consumer) | Notes |
|---|---|---|
| `MysqlDriver.getColumnLength` (`driver/mysql/MysqlDriver.js`) | every `@Column({ type: 'uuid' })` on an entity | MySQL has no uuid type (`uuidColumnTypeSuported` is true only on **MariaDB ≥ 10.7**), so `uuid` normalizes to `varchar`. The driver returns `36` **only** when `generationStrategy === 'uuid'` (`@PrimaryGeneratedColumn('uuid')`); a plain FK/relation uuid column falls through to the generic varchar default **255**. Hence `auth_users.id` is `varchar(36)` while `auth_users.realm_id` is `varchar(255)` — both correct, both derived. Migration `1785871780234-AlignSchemaWithEntityMetadata` widened the 15 columns where hand-authored migrations wrote `varchar(36)`. Upstream fix for the non-generated case (typeorm#1139) only ever covered the generated one. |
| `EntityMetadataValidator.validate` (`metadata-builder/`) | — (blocks pinning `length` on uuid columns) | `if (column.length && !driver.withLengthColumnTypes.includes(normalizedColumn)) throw` — so `@Column({ type: 'uuid', length: 36 })` fails at `DataSource.initialize()` on postgres with `Column X of Entity Y does not support length property.` (verified empirically 2026-07-29). **This is the hard reason the MySQL uuid width cannot be fixed from the entity side** — the app would not boot on postgres at all. `uuid` is absent from postgres's `withLengthColumnTypes`; on MySQL the same column normalizes to `varchar`, which accepts a length, so it passes there. |
| `PostgresDriver.createFullType` (`driver/postgres/PostgresDriver.js:1011`) | — | Appends `(length)` whenever `column.length` is set without consulting `withLengthColumnTypes`, so a direct call renders `uuid(36)`. Unreachable from entities (the validator above throws first) and from introspection (query runners read a length back only for `withLengthColumnTypes`), i.e. an API-level inconsistency rather than a live bug — postgres + cockroachdb read `column.length` directly, mysql/oracle/sqlserver render through `getColumnLength`. Filed as **typeorm/typeorm#12741**, fix in **typeorm/typeorm#12742**. Community repo — treat as a fixed constraint regardless. |
| `RdbmsSchemaBuilder.log()` (via `dataSource.driver.createSchemaBuilder()`) | — (upstream mechanism; the gate calls typeorm-extension's `getSchemaDrift`, which wraps it) | Returns the statements that would reconcile the live schema with the entity metadata. Zero = migrated schema matches the model. Wired as the 4th step of the `tests-migrations` CI job; also the tool that found both wrong-target FKs and the naming/type split. With the chain applied, `migration generate` correspondingly writes **no file**. |
| `ColumnMetadata.generationStrategy` | `@PrimaryGeneratedColumn('uuid')` vs `@PrimaryColumn({ type: 'uuid' })` | The distinction is load-bearing for the width above: `auth_consents.id` (generated) is 36, `auth_events.id` / `auth_session_tokens.id` (app-provided ids) are 255. |

| typeorm-extension (source) | authup (consumer) | Notes |
|---|---|---|
| `useEnv` (`dist/index.mjs` environment reader) / `readDataSourceOptionsFromEnv` | `apps/server-core/src/app/modules/config/read.ts` | `readDataSourceOptionsFromEnv()` consumes both the preferred `DB_*` names and their `TYPEORM_*` aliases through the memoized `useEnv` registry. |
| `synchronizeDatabaseSchema` (`src/database/methods`) | `app/modules/database/module.ts` → `DatabaseModule.migrate` | Runs `runMigrations({ transaction: migrationsTransactionMode })` when the options carry migrations, else `synchronize(false)`. So for mysql/postgres **boot applies pending migrations** — a failing migration is a failed startup, not a CLI error. sqlite has `migrations: []` and synchronizes. |
| `generateMigration` (`src/migration`) | `apps/server-core/src/cli/commands/migration.ts` → `migration generate` | Drops + recreates a local `migrations` database per dialect, replays the chain, diffs against the compiled entities, writes **both** dialect files under one shared timestamp, `prettify: true`. Hardcoded local connections matching `docker-compose.yml` (postgres 5432 / mysql 3306, `start123`). Emits nothing when there is no diff. This is the only sanctioned way to author DDL (conventions.md). |
| `assertSchemaMatchesMetadata` / `getSchemaDrift` (4.0.0-beta.2) | `scripts/assert-schema-drift.mjs` | The gate calls `assertSchemaMatchesMetadata(options, { skipWithoutMigrations: true })`, which throws `SchemaDriftError` listing the reconciling statements; `skipWithoutMigrations` skips sqlite for free. Shipped in beta.2 (tada5hi/typeorm-extension#1422) in response to **#1420**, filed from this work. The `typeorm-extension db drift` CLI does the same job but discovers a DataSource from a **file**, while authup builds its options programmatically (`DataSourceOptionsBuilder` injects entities, migrations and subscribers around the env-derived connection), so the thin script stays. |
| `renameIndex` / `renameForeignKey` / `changeColumnType` / `withForeignKeyChecksDisabled` (4.0.0-beta.2, beta.3) | **not consumed** | Guarded, idempotent rename/widen helpers, filed and shipped from this work (#1420 -> #1422, #1424 -> #1425). `1785871780234` was first written on top of them and then rewritten as plain SQL: a migration should be a list of statements, not a program, and the idempotence they buy is a property no other migration in the chain has (the `migrations` table is what prevents re-runs). Reach for them if a future repair genuinely needs to resume mid-run. |
| `MysqlQueryRunner.changeColumn` (typeorm) | — (why `1785871780234` writes `MODIFY COLUMN` by hand) | It DROPs and re-ADDs a column whose length differs, so a widening empties the column on a populated table and fails outright on a foreign key column (`ER_FK_COLUMN_CANNOT_DROP`, even with the checks disabled). This is also why a generated mysql migration for the width drift was data loss rather than a widening. |
| `MysqlQueryRunner.changeColumn` / `PostgresQueryRunner.changeColumn` (typeorm) | `1788782400000-WidenClientSecret`, hand-written on BOTH dialects | The postgres runner takes the same drop-and-re-add branch when `type` or `length` differs (confirmed against `PostgresQueryRunner.js` for plan 105, 2026-09-07), so `migration generate` for `auth_clients.secret` `varchar(256) -> varchar(512)` (an encrypted secret is a cipher blob of about 420 characters) emits `DROP COLUMN` + `ADD` on each dialect and empties every client secret, `system` included. The migration writes `ALTER COLUMN "secret" TYPE character varying(512)` / `MODIFY COLUMN secret varchar(512) NULL` by hand, which widen in place; its `down()` narrows back and fails (strict mode on mysql) while a row holds a value longer than 256, which is exactly an encrypted secret, so such clients are rotated to another mode before a revert. Committed DDL the generator did not produce, per the `1785871780234` precedent; the populated round-trip (`npm run test:migration-latest`) is the gate that proves the widening keeps rows. |
| `assertSchemaMatchesEntity` (`@rapiq/adapter-typeorm`, not this package) | `app/modules/database/repositories/schema-validation.ts` | Different axis: validates rapiq query **schemas** against entity metadata at boot. The drift gate validates the **migrated database** against entity metadata in CI. Both are needed. It does NOT cover schema `indexes` declarations (rapiq 2.0.0-beta.20) — authup carries its own `assertSchemaIndexesMatchEntity` (leftmost-prefix check against `metadata.primaryColumns` / `uniques` / `indices`) until upstream grows one. |
| `PostgresQueryRunner.loadTables` index query (`driver/postgres/PostgresQueryRunner.js`, typeorm 1.1.0) | postgres `down()` of `1786631686318-SortIndexesAndAccountUniqueness` | Reads index columns via `"a"."attnum" = ANY ("ix"."indkey")` with no `ORDER BY` on the indkey position, so a pre-existing composite index comes back in physical column order (`attnum`), not index order. The generated `down()` for the #3442 uniqueness flip therefore recreated the index as `("provider_id", "provider_user_id")` although the chain had created it as `("provider_user_id", "provider_id")`; it was corrected by hand so a revert restores the released chain byte-identically (pinned by observation on `pg_indexes`), one of the documented exceptions to committing generated DDL untouched. Harmless for the drift gate either way because of the row below. |
| `RdbmsSchemaBuilder.shouldDropIndices` (`schema-builder/RdbmsSchemaBuilder.js`, typeorm 1.1.0) | drift gate / `migration generate` index comparison | Compares an entity index against a live one by `isUnique`, `isSpatial`, the driver's index type, `isFulltext`, column count and `columns.every(c => tableIndex.columnNames.indexOf(c) !== -1)`: **order-insensitive** on the column set. So the swapped order above is not drift, while a uniqueness flip is (which is what the #3442 migration generated). |
| MySQL implicit FK indexes (InnoDB behavior, not a typeorm API) | mysql `down()` of `1786436332251-QueryIndexes` | InnoDB auto-creates an index per FK (named after the constraint) and **silently drops it** when a later `CREATE INDEX` can serve the constraint — verified empirically 2026-08-11 (`auth_user_roles.user_id`: the `FK_a3a…d`-named index vanished when `IDX_a3a…` was created). The generated migration `down()` is not FK-aware, so its `DROP INDEX` on such a column fails with ER 1553 mid-way (non-transactional DDL → partial revert state). Pattern: wrap the generated statements with hand-authored DROP FOREIGN KEY / ADD CONSTRAINT phases; `ADD CONSTRAINT` recreates the implicit index under the constraint's own name. Affected-set query: FK columns whose ONLY leading index (information_schema.STATISTICS `SEQ_IN_INDEX=1`) is one the migration created. |
| `IndexMetadata.build` (`metadata/IndexMetadata.js`) and the `Index(name, { synchronize: false })` overload (`decorator/Index.d.ts`), typeorm 1.1.0 | the four `@Index('IDX_auth_*_global_name', { synchronize: false })` declarations behind `1788793885495-GlobalEntityUniqueness` (issue #3559) | An index with `synchronize: false` takes `name = givenName` and returns BEFORE resolving columns: a name-less declaration has `name` undefined, matches no live index, and the builder drops the live one as unknown. The unsynced overload is name-only (a column list or `unique` fails the overload resolution, TS2769), so the columns, the expression and the uniqueness exist in the migration alone. `RdbmsSchemaBuilder.shouldDropIndices` returns false for a matched unsynced index and `Table.create` / `createNewIndices` filter `synchronize === true`, which is what lets hand-written expression-index DDL coexist with the drift gate (verified 2026-09-07 by the spec's before/after `log()` on both dialects). |
| `EntityMetadataBuilder` unique-as-index mapping on MySQL | why those names are given, not derived | MySQL stores a `@Unique` as a unique INDEX named by `namingStrategy.indexName(...)`: the released `Default` migrations carry `IDX_561d1b8a5a7db602df418d7cd5` for `auth_permissions (name, client_id, realm_id)`, so the derived index name over the same column list is already taken there and the expression index needs a name of its own. |
| `PostgresQueryRunner.loadTables` / `MysqlQueryRunner.loadTables` with expression key parts | the drift gate over the four expression indexes | Postgres joins `pg_attribute` on `attnum = ANY(indkey)` and an expression key part has attnum 0, so the loaded `TableIndex` carries only the plain columns; mysql reads `information_schema.STATISTICS`, where a functional key part has `COLUMN_NAME NULL`. Neither loader fails, and both keep the NAME, which is all the builder compares for an unsynced index. |
